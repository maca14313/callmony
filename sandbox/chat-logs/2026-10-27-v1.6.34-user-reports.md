# v1.6.34 — user reports (2026-10-27)

The user tested v1.6.33 (vc44) on their phone and sent eight reports.
Verbatim quotes below, each followed by the decode and the fix that
shipped in v1.6.34.

---

## 1. The call cards were made transparent

> "you did say Lighter call cards but you did make it transparent why"

**Decode.** v1.6.33's port of the v1.6.30 flat-and-light card removed the
per-row chrome entirely — no fill, no border, no corner, just an inset
hairline under a row sitting directly on the canvas. "Lighter" was meant
as *visually lighter*; the user read (correctly) *transparent*.

**Fix.** The card is a real surface again: a solid `C.card` fill (opaque,
clearly lifted off the canvas in both themes) with a hairline border and
14dp corners — while keeping every lighter metric from the flat pass
(44dp avatar ring, 15sp title, 12sp meta, compact 10/8dp padding). The
transparent-row inset hairline is gone.

## 2. Speed

> "make this app the fastest app ever"

**Decode + fix.** A perf pass over the heaviest recomposition paths, with
the launch structure (splash → hydrate, onCreate window) untouched per
the standing iron rule: the Recents headline owe sums, the missed count
and the paged slice are `remember`-keyed (they rescanned the whole
entries list on every state flip — real work per frame with a busy
book); the General screen's two hero sums are remembered on the people
list. Boot itself was already concurrent-cached since v1.6.27/28.

## 3. PIN — forgot password not needed

> "for pin i think forgot password is not needed for now"

**Fix.** The "Forgot PIN?" link is removed from the lock screen. The PIN
stays a pure lock; the in-app Backup → Restore remains the data path.

## 4. The owe tabs' filter axis (the correction)

> "what i wanted was when one of the Filter Buttons (They owe you / You
> owe them) are clicked to be different kind of tabs that help filter
> like custom date, by amount, by name, other useful filters… dont do
> that [the Call Log / Contact rows]"

**Decode.** The v1.6.30/33 attempt stacked the CALL-DIRECTION chips
(All/Missed/Incoming/Outgoing/Favorites — the user paraphrased them as
"Call Log / Contact rows") under the owe buttons. The user wants the
FILTER axis: date windows, amounts, names.

**Fix.** An active owe tab now opens a side-scrolling row of three filter
chips — **Date** (Any time / Today / Last 7 / Last 30 / CUSTOM RANGE with
native from-to pickers), **Amount** (Any / 100 / 500 / 1,000 / 5,000+
on the contact's |balance|), **Name** (Newest / A→Z / Z→A; a name-sorted
view goes flat, no day headers) — each showing its current selection,
each opening its own sheet. The direction chips return to their only
home: the sticky day header in the "all" view. The Recents nav reset
clears every sub-filter. Pipeline: pure `applyOweFilters` (new
`OweFiltersTest`, 6 cases). 16 i18n keys ×5 languages.

## 5. The calculator's native text menu (the correction)

> "PASTE should be what someone can do in a normal input or text area,
> like press long on some part of word and native options shows up like
> copy, paste, cut and others"

**Decode.** v1.6.33's custom long-press-copy + PASTE chip was NOT the
ask — the ask is the OS's own text menu on an ordinary editable field.

**Fix.** The display is now the keypad's `NoImeNumberField` (a real
editable field, IME suppressed): long-press any part of the text → the
NATIVE menu (Copy · Cut · Paste · Select all) with selection handles.
Edits land through `mapDisplayExpr` (ASCII operators/comma decimal →
display glyphs, unevaluable characters dropped, length capped at 80);
editing a shown result starts a fresh expression. `NoImeNumberField`
grew `alignEnd` + `maxLines` (display right-aligns, wraps to 3).
New `V1634CalcDisplayTest` (4 cases).

## 6. The quick item belongs inside ADD ITEM (the correction)

> "the quick item should be inside ADD ITEM as scrolling tabs: Items
> (qty × price), Quick item, Just amount, other useful types"

**Fix.** The v1.6.27/29 label+price row is GONE from the ledger view.
The entry editor now carries a horizontal scrolling tab strip: **Just
amount** (the classic hero field) · **Items · qty × price** (the full
line-item editor) · **Quick item** (label + price + ＋ → a qty-1 item,
amount follows the total) · **Recent** (one-tap reuse of items booked
before — distinct labels with their last price, newest first). Item rows
+ total stay visible under every tab; tapping a row jumps to Items for
editing. New `EntryEditAddTabsTest` (2 harness cases) + `RecentItemsTest`
(3 cases).

## 7. THE DATA LOSS — "every time i install the app the data is all gone"

**Decode (the audit).** The storage layer is sound: the JSON loader is
shape-sanitized (bad rows skipped, never written back), saves fire only
on explicit mutations, hydrate never writes, and every APK since v1.6.13
is signed with the same key (apksigner-verified each release) — so an
UPDATE install keeps 100% of the data. What wipes the phone is the
UNINSTALL: an uninstall (or an OEM installer's "reinstall" update flow —
common on the budget Tecno/Infinix ROMs this user is on) deletes the
app's whole private storage, and the cloud Auto Backup rarely restores
sideloaded apps in time. That is the install path the user hits every
release.

**Fix (the no-data-loss layer).** Every time the app leaves the screen
(`onStop`) — plus once per boot as a safety net — the FULL store is
mirrored to `Downloads/Callmony/callmony-backup.json` via
MediaStore.Downloads: public, user-visible, the documented home for
files that must outlive the app, and readable back by the reinstalled
app with no permission prompt (the MediaStore row's owner package
matches again after reinstall). On the next fresh boot with an empty
store the app OFFERS the backup back with one tap — Restore brings the
whole store including the onboarded flag, so the phone continues exactly
where it left off. Guards: an empty/unhydrated store can never overwrite
the backup; the danger-zone wipe removes the file too; Settings → Backup
shows the layer's status. Triggers run strictly POST-launch (onStop +
hydrate-complete); the onCreate/setContent window is untouched. iOS is a
no-op (the container rides the device backup). New `AutoBackupOfferTest`
(4 cases).

## 8. The PIN 4th dot

> "the PIN 4th dot gets coloured every time but not on the fourth"

**Decode.** The v1.6.25 fix (160ms submit delay so the 4th dot paints
before the unlock/shake recomposition) was applied ONLY to the
LockScreen. The set/change/remove PIN sheet in Settings still submitted
synchronously in the same frame the 4th digit landed — and every submit
path ends with `entered = ""`, so the dots recomposed straight back to
empty and the 4th dot never painted filled.

**Fix.** The same LaunchedEffect(entered) + 160ms pattern now covers the
PIN sheet too.
