## The decode (every frame accounted for, read bottom-up)

1. `NoImeFieldActual.kt:142` — `et.setText(span)` runs INSIDE the AndroidView
   `update` block. The report's own frames prove the phase: the update lambda
   executes during `CompositionImpl.applyChanges`, i.e. in the MIDDLE of the
   composition APPLY pass (`Recomposer$runRecomposeAndApplyChanges →
   applyChanges → Operation$UpdateNode.execute → update`).
2. On a real device, `EditText.setText` →
   `Editor.maybeFireScheduledRestartInputForSetText` →
   `InputMethodManager.restartInput` → `startInputInner` →
   `TextView.onCreateInputConnection` (TextView.java:9753 on Android 12) —
   and TextView's own implementation calls **`focusSearch(FOCUS_DOWN)`**
   hunting for the next text editor below.
3. That focus search hands into Compose (`AndroidComposeView.focusSearch`),
   walks the tree, and goes **beyond the visible bounds of a LazyList**
   (`searchBeyondBounds`) → `LazyListBeyondBoundsState.remeasure` →
   `forceRemeasure` → LazyLayout `subcompose` (`createItemsAfterList`
   measures items AFTER the visible list) → a fresh `composeInitial` on a
   subcomposition → `drainPendingModificationsForCompositionLocked` →
   **ComposeRuntimeError: "pending composition has not been applied"** —
   re-entering composition while the parent's changes are still being
   applied is illegal, so the process dies.

One root cause, both reported symptoms: the synchronous beyond-bounds focus
traversal ran on EVERY keystroke (the lag), until one re-entrant subcompose
threw (the close). Why no harness ever saw it: Robolectric's shadow IMM makes
`startInputInner` a no-op, so the chain's FIRST link never fires in tests —
only on a real Samsung/OneUI build. That is why v1.6.42's 300-key stress
battery proved "the Compose layer innocent" while the device still crashed:
the harness literally cannot build this stack.

## The fix — two independent layers (either alone breaks the chain)

- **Layer 1, the door is shut**: new `NoImeEditText` subclass whose
  `onCreateInputConnection` returns `null`. This field never talks to an IME
  (`setShowSoftInputOnFocus(false)` since v1.6.15; the 12-key grid IS the
  input method), so the entire chain — which ENTERS through
  TextView.onCreateInputConnection's focusSearch — never starts:
  `startInputInner` gets null and returns instantly. No focus search, no
  beyond-bounds remeasure, no re-entrancy, no per-keystroke IMM churn. The
  native long-press menu (Copy · Cut · Paste · Select all) and the selection
  handles are untouched (the Editor's ActionMode path never touches the
  InputConnection), and the view still reports `onCheckIsTextEditor() ==
  true` so it is treated as a proper editor.
- **Layer 2, the write leaves the apply phase**: the `update` block now
  NEVER calls `setText` synchronously. It records the latest pending
  text/highlight/highlight-colour and posts ONE single-flight runnable on
  the view; the runnable runs on the main looper AFTER the composition has
  fully applied and does the programmatic-guarded `setText` + caret-at-end
  with the LATEST pending values (however many recompositions land first,
  one runnable, newest value wins). Re-entrancy is now structurally
  impossible — even an OEM-only side-effect of setText can never re-enter
  the runtime mid-apply again.
- Kept from the previous rounds: the v1.6.43 no-op fast-exit (a
  nothing-changed recomposition still touches the view zero times), the
  v1.6.42 guarded focus requests and cached colour/size writes (those only
  SCHEDULE a traversal, they cannot re-enter one), the crash firewall
  itself (logcat + crash-last.txt + crash-history.log + clipboard + next-boot
  hand-over — it just proved its worth by delivering this very report).

## The regression battery (NEW NoImeFieldV1644Test ×3)

1. `theCrashDoorIsShut_noInputConnectionEver` — a fresh `NoImeEditText` AND
   the exact instance the composition builds both offer NO InputConnection,
   while still reporting as a text editor (the native menu's precondition).
2. `textWritesNeverRunInsideTheCompositionApplyPhase` — THE STRUCTURAL
   PROOF: a `SideEffect` that runs in the SAME apply pass, right AFTER the
   update block, must still see the OLD text when the state changes (under
   v1.6.43 it already saw the new one — the exact re-entrancy that crashed);
   the posted write then lands on the looper with the caret at the end.
3. `highlightedSpansLandThroughThePostedPath` — the exact crashing branch
   (the highlighted span write at the old :142) lands its per-character
   colours through the posted path and re-posts on later edits.
