## The six fixes

**#1 — THE ENTER KEY IS THE NORMAL ENTER, AND THE SPACE KEY JOINED ITS
ROW**: v1.6.46's ENTER was a full-width action bar doing exactly what
Next does (commit + save). The user's round-two report corrected both
halves: "the inter btn is not the next btn it is the normal inter btn
like in the netiv keyboard and in its row add the space key too". The
bottom row is now the NATIVE keyboard's bottom row — a WIDE BLANK SPACE
BAR (card fill, hairline border, no glyph) with a NORMAL-WIDTH
brand-filled ENTER key on its right, a peer of the five key rows (the
pad keeps its 264dp, six rows at ~37dp each; the v1.6.43
direct-measurement reservation and the 193dp band invariant are
untouched). And the enter key is THE NEWLINE: `onEnter` now runs
`commitCalcLine()` alone — the active line locks into the ledger, a
fresh line takes over, and NOTHING is persisted by it. Next is the one
commit+save key (v1.6.46 report #3's contract), the 600ms autosave and
the leave-time create close every other hole, so a newline-only session
still persists on the way out. The SPACE key appends one space (never
doubling one) through the undoable funnel with no text-keyboard mark —
adjacent numbers keep folding as +, so "185 40" reads 225.

**#2 — WHY THE NATIVE KEYBOARD SOMETIMES SHOWS IN NUMBER MODE (the
question answered, and the door welded shut)**: the QWERTY/title fields
are served by the system IME, and the leak's remaining path never
touches the number field — open the payment sheet from the sum total's
Pay chip (its amount/note fields take focus and raise the system
keyboard), close it, and the keypad comes back while the IME LINGERS on
screen: no editor is served, the num field never regains focus, so
v1.6.45's field-level force-hide has nothing to trigger on; OEM re-shows
on window focus are the same story. So while the calc keypad is up, the
WINDOW ITSELF now refuses the soft keyboard: a new
`UiPlatform.setImeSuppressed(Boolean)` (interface default no-op; the
Android actual stores the window's soft-input mode, sets
SOFT_INPUT_STATE_ALWAYS_HIDDEN and fires an immediate IMM hide, and
restores the saved mode on the lift). The live Activity is registered
into AndroidUi from MainActivity.onCreate and cleared in onDestroy. The
suppression arms and lifts with `wantPad` itself (keypad up / down /
sheet open / editor leaving — the canvas's dispose restores it, so a
leaked ALWAYS_HIDDEN window can never eat the QWERTY in text mode), and
the Compose-side `ime.hide()` stays as the instant belt.

**#3 — BULLETS OR NUMBERS AT THE START OF EACH LINE, CHANGEABLE**: a
small chip between the canvas title and Σ cycles the prefix style —
• (the DEFAULT: lines show bullets from the first commit) → "1." "2."
"3." → none. The chip's glyph is the style itself. Every committed line
leads with its prefix (a faint 20dp column before the calculation), the
ACTIVE line carries its own (the bullet, or the number this line will
take once committed), and the choice rides the entry as the new
optional `LedgerEntry.calcPrefix` (absent = bullet — the exprNote
pattern: old rows decode, old code ignores, backups mirror). It also
rides the autosave key so a prefix change alone persists.

**#4 — THE PAYMENTS FREEZE, KILLED ("sometimes it adds it, sometimes it
not, or it will not update it")**: the root cause was found in the old
`paymentsOverride` — the moment a line was UNLOCKED or DELETED, the
editor SNAPSHOT the payment list and served that frozen copy on every
later read: a payment recorded through the sheet never showed on the
total ("it will not update it"), and the NEXT save persisted the stale
list — WIPING the recorded payment out of the store ("sometimes it
not"). The remap is now keyed by PAYMENT ID: `payRemap:
Map<String, Int?>?` — the LIVE store list flows through it on every
read (`remember(payRemap, currentEntry)`), payments recorded later pass
through untouched, unlock/delete shift only the payments that existed at
their line indices, and every save carries the live list.

**#5 — THE "WEIRD DIFFERENT MODALS", EXPLAINED AND CLEANED**: (a) the
LOCK PILL's tap flipped a locked/unlocked state whose only remaining
job since v1.6.45 (per-line pay chips → the sum total) was recolouring
the block — the pill and `unlockedLines` are GONE; the line is one calm
strip (prefix · text · date · own total, copy + delete at the end) and
only a DELIBERATE long-press pulls it into editing (the v1.6.39
affordance, kept — tested). (b) A plain tap on a committed line does
NOTHING (the row keeps an inert click so it can never open anything).
(c) What still opens modals ON PURPOSE, so it never surprises: the Pay
chip beside the sum total (the payments modal = the history's entry
point), the ✕ on each line (the delete confirmation), and touch-and-hold
ON a text field (the phone's own Copy/Cut/Paste menu — kept, it is the
native editing surface).

**#6 — THE LEDGER'S CIRCULAR ＋ AND THE CANVAS CARDS**: while the ledger
tab is showing (General tab's ledger segment OR a contact's ledger tab),
a 54dp brand circle pins to the content area's BOTTOM-END. It is
published by LedgerSection into a new shell-level `RootFab` slot
(Kit.kt) rendered in CallmonyApp ABOVE the tab screens AND the whole
overlay stack (the contact detail is an overlay that embeds its own
ledger — the slot renders above it) but below the sheets; it hides
whenever any overlay sits above the ledger surface (the EntryEdit the
FAB itself opens, search, settings…) and returns the moment it closes.
The full-size wrapper Box consumes no input — only the circle is
clickable. The tap opens `Overlay.EntryEdit(null, ownerId)` — the editor
starts with the full-screen canvas already up: ONE TAP, ONE NEW CANVAS.
And the entry list became CANVAS CARDS: every entry leads with its own
PAY-PERCENTAGE RING (34dp: the sweep fills with the paid fraction, green
once done, the PERCENTAGE PAID in its centre — 40% at a glance;
entries with nothing payable keep the old kind badge), the CANVAS TITLE
heads the card (calcTitle → quick-item label → kind label), the subtitle
carries the calculation's first line (the @date marker stripped) with
the date · balance · payment count, and THE STATUS rides the card
without expanding: ✓ Paid / Paid 200 / 500 / Pending 500 / Overpaid by …
The chevron detail (items, full payment history, actions) is unchanged.

## Harness notes

  * Descendant tags inside combinedClickable/clickable rows MERGE into
    the row's node — the line-prefix tag and the card-ring tag both need
    `useUnmergedTree = true` to be found (the v1.6.42 lesson, hit twice
    more).
  * The store is a JVM singleton ACROSS CLASSES: the first full-suite
    run failed three tests on poisoned amounts (275/345 clashed between
    the V1646 and V1647 batteries; 300 is already owned by the older
    ones). The new batteries write only unique amounts (185/225/230,
    305/315, 430, 888/890).
  * Committed adjacent numbers serialize with an EXPLICIT "+" ("275 70"
    commits as "275 + 70") — the exprNote assertion in the newline test
    was written against the raw spaced form first and failed on exactly
    that.
