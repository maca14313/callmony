# v1.6.20 user reports + fix map (2026-10-26)

## Verbatim user report (round 3 of the freeze saga)

> 1. still the same , the app is freezing and crushing. make it to show the
>   problem in the app, when it is trying to close

Context: the v1.6.19 round had root-caused and fixed the welcome-screen
freeze (infinite boot spinner under the onboarding sheet) and verified it in
two boot harnesses — but the user's device STILL froze and closed. The user
explicitly asked for the app to SHOW the problem instead of silently dying.

## What was shipped (v1.6.20, versionCode 30)

Instead of guessing at a cause the sandbox cannot reproduce, the app now
diagnoses itself and surfaces the problem on screen at the exact moment it
is trying to close:

1. **ANR watchdog** (androidMain `lib/DiagAndroid.kt` + pure accounting in
   commonMain `lib/Diag.kt` — `BlockageDetector`). A daemon thread posts a
   heartbeat to the main handler every second and catches both freeze
   shapes:
   - **hard blockage** — no heartbeat has RUN for ≥ 5 s (main stuck inside
     one message: binder call, deadlock, tight loop that never returns to
     the looper);
   - **saturation** — the heartbeat runs but ≥ 4 s late (main returns to
     the looper between messages, yet every slot is eaten — the v1.6.18
     forever-spinner class of freeze).
   On detection: the main-thread stack + boot phase + app-state snapshot
   are captured and reported once per 60 s episode.

2. **Diagnostics screen in its own `:diag` process** (`diag/DiagActivity`)
   — plain Views (no Compose, no app runtime), so it comes up even while
   the main process is frozen solid or dying. It pops OVER the frozen app
   with the headline, phase, monospace stack + state card and
   Copy report / Reopen app / Close buttons. Labels reuse the commonMain
   i18n dictionaries (language read from the persisted settings, same
   trick as the splash-theme resolution).

3. **Crash firewall** — chained `Thread.setDefaultUncaughtExceptionHandler`:
   captures exception + main stack + phase + state, saves the report,
   shows the diagnostics screen, waits ~2.6 s, then hands to the platform
   handler so the process still dies cleanly. Skips itself in the `:diag`
   process (no recursion) and under Robolectric.

4. **In-app overlay** (`ui/overlays/DiagnosticsOverlay.kt`) rendered above
   everything, even the lock screen:
   - live freeze caught this session ("The app just froze — here's what was
     blocking it", shown the moment the app recovers);
   - unseen report from the previous run ("Callmony froze and was closed
     last time") — if the system ANR-kills the app anyway, the report
     persists (own `filesDir/diag` Properties store — deliberately outside
     the app's Persist queue so a frozen app can't deadlock its own
     diagnostics; capped at 12) and shows at next launch;
   - Settings → new **Diagnostics** section (red badge for unseen reports,
     expandable rows, per-report copy, Clear all).

5. **Boot-phase tracker** — `app.init → app.ready → activity.create →
   activity.content → ui.compose → ui.splash → store.read → store.loaded →
   ui.main → ui.onboarding → ui.idle`. Every report carries the phase it
   was captured in, so "it freezes at the welcome screen" becomes an exact
   machine-observed answer (`phase: ui.onboarding` + the blocking stack).

6. i18n: 20 `diag.*` keys × 5 languages (1045/1045 parity, 0 missing).

## Verification

- Pure battery 54/54 green (DiagTest ×8 new — detector hard-blockage /
  saturation / cooldown accounting, record/seen/dismiss flow, live-vs-
  pending priority, report text, snapshot; plus V1618 16, ReminderV1617 9,
  SearchContacts 12, CalcFormat 5, KmpDate 4).
- Two detector bugs were caught BY the new tests and fixed before shipping:
  `hardBlockageMs` must measure from the last heartbeat RUN (not the post),
  and `t=0` is a valid clock value (explicit once-flags instead of 0
  sentinels).
- BootDiagTest (fresh install) GREEN — 150 pumps, no hang, boot phase
  reached `ui.idle` (new assertion: the phase must advance past the splash,
  so a future welcome-screen hang fails CI loudly). UpgradeBootDiagTest
  GREEN.
- Android compileDebugKotlinAndroid + both iOS targets (iosArm64,
  iosSimulatorArm64) compile clean (iOS DiagStorage actual follows the
  IosKv Foundation pattern; commonMain has no synchronized/@Volatile — the
  known Kotlin/Native constraint).
- Release APK: com.callmony 1.6.20 vc30 minSdk 23 targetSdk 34, signed
  CN=Callmony ET; `com.callmony.diag.DiagActivity` with `android:process
  ":diag"` verified inside the compiled manifest via aapt.

## What the user will see next time it freezes

The frozen app gets covered by the dark diagnostics screen ("Callmony
froze" in their language) with exactly what was blocking — and the same
report is one tap away from the clipboard via **Copy report** to send back.
If the system kills the app before they can read it, next launch opens on
the same report automatically.
