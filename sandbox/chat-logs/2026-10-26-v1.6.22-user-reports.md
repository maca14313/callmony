## The decode — what changed vs the v1.6.20 report, and what it means

1. The main thread is **RUNNABLE**, not parked in `SnapshotKt.readable`.
   The v1.6.21 fix (plain-field `lastActive`, single-writer snapshot rule)
   did its job — there is no snapshot collision left, and the full thread
   dump proves no background thread holds anything (all workers parked).
2. The stack is the SAME gesture observer (`CallmonyApp$10$1$1` /
   `awaitEachGesture`), but the sample caught it at **ForEachGesture.kt:102
   — the `while (currentContext.isActive)` LOOP CONDITION** (v1.6.20's
   sample caught :104, the `block()` call inside the loop).
3. RUNNABLE + no progress 5003 ms + parked-at-a-trivial-atomic-read =
   **the main thread is executing that `while` loop over and over**. The
   touch-dispatch frames above it in the stack are still waiting for
   `invokeSuspend` to return — it never does.

## The root cause (present since v1.6.17)

```kotlin
.pointerInput(Unit) {
    awaitEachGesture {
        lastActive.v = now()      // writes a field… and returns. NEVER awaits.
    }
}
```

`awaitEachGesture`'s contract REQUIRES the block to await at least one
pointer event — internally it is `while (isActive) { block() }`. A block
that returns without suspending turns that into an **infinite busy-spin on
the main thread**:

- v1.6.17–v1.6.20: the spin's body wrote `mutableStateOf` state every lap →
  snapshot storms → the v1.6.20 report (BLOCKED in `SnapshotKt.readable`).
- v1.6.21: the snapshot write was removed (correct, but only half the
  story) → the spin kept spinning, now at pure 100% CPU → this report
  (RUNNABLE at the loop condition).

From the **first touch on the main UI** the looper never returns to the
queue: our watchdog fires at 5 s, Android's input-dispatch ANR fires at 5 s
("Callmony isn't responding" → Close app = the "crushing"), and the
:diag-process screen pops with the report. It also explains why the
Robolectric boot harnesses stayed green: with no touch events ever
dispatched in the harness, the handler coroutine stays parked at its first
await and the spin never starts.

## The fix (v1.6.22)

The observer now awaits the down FIRST, then refreshes per event until all
pointers release — the loop parks between gestures at ~zero CPU, still a
pure non-consuming observer (`requireUnconsumed = false`, nothing
consumed → every tap/swipe/child gesture exactly as before):

```kotlin
.pointerInput(Unit) {
    awaitEachGesture {
        awaitFirstDown(requireUnconsumed = false)
        lastActive.v = now()
        while (true) {
            val event = awaitPointerEvent()
            lastActive.v = now()
            if (event.changes.all { !it.pressed }) break
        }
    }
}
```

Audit: every other `pointerInput` in the app (SwipeRow ×3, KeypadSheet,
Calculator) uses `detectTapGestures` / `detectHorizontalDragGestures` —
framework detectors that always suspend. Safe.

## Diagnostics hardened (so the next report settles it in one read)

`captureFreezeReport` now embeds a **3-sample main-thread spin probe**
(200 ms apart): identical stacks → hard block; the same top frames
wandering → spin/livelock (exactly the v1.6.21 signature that a single
sample made look like an innocent transient); different stacks every
sample → saturation.
