## The five fixes

**#1 — the ENTER key, "just like in the native keyboard", "on the right
bottom under the -":** a WIDE, brand-filled ENTER bar fills its own 34dp
action row UNDER the ± 0 . − row — full-width (the native return key's
wide-bottom-row look), carrying the return glyph only (new
`keyboard-return` icon in Icons.kt: arrowhead + shaft + riser built from
three filled shapes), never labelled, never disabled (native keyboards
don't disable enter). CALC_PAD_H grew 224 → 264dp so the five key rows
KEEP their ~37dp height — the enter row is extra, not squeezed-in — and
the canvas's v1.6.43 direct-measurement reservation absorbs the taller
pad for free (the pinned band becomes 264 − 71 = 193dp; V1643's invariant
updated, the ENTER-under-− geometry + ≥30dp key sizes pinned there too).
The tap runs `commitAndSave()` — the same action as Next.

**#2 — the pay btn beside the TOTAL text and the circle, percentages
only:** the sum total collapsed from two rows into ONE — the 40dp PAY
RING (sweep fills with the paid fraction, brand → green when done) with
the PERCENTAGE LEFT in its centre, the TOTAL label + amount (+ items, +
paid · remaining once anything is paid), then THE PAY CHIP and the copy
button on the same row. The percentage is `round(remaining/total × 100)`
coerced 0–100 — "100%" unpaid → "0%" done — and NOTHING counts lines out
loud any more: the v1.6.45 LeftCircle, its "N left" caption, the
`calcLeftCount` FIFO walker and its two pure tests, and the `ee.calcLeft`
key in all five languages are all gone (the FIFO ledger logic survives in
git history if ever needed).

**#3 — "the next btn also should do what the save btn does … we dont need
the save btn":** Next now commits the line AND saves the entry; the canvas
Save button and the sheet's footer Save button are both REMOVED (the
sheet's footer band itself is gone — the form scrolls longer). Three
pieces of engineering make it safe:
  * THE SAVE PULSE — `commitAndSave()` bumps a pulse and a
    `LaunchedEffect` does the `save(silent = true)` one recomposition
    LATER, because a same-handler save would read the PRE-commit
    `effAmount`/`calcNote` vals (captured before `commitCalcLine()`
    mutated the ledger — the entry would have been built from stale
    derived state, double-counting the just-committed line).
  * THE LEAVE-TIME CREATE — backing out of a never-saved draft with
    anything payable CREATES it (`leaveSave`), so the removed Save button
    can't eat a typed-but-never-committed calculation. The action is
    refreshed through `rememberUpdatedState` because a plain
    `DisposableEffect(Unit)` onDispose closure FREEZES composition #1's
    derived vals — the old dispose-save had exactly that latent
    staleness in its debounce-tail path (fixed for live entries too).
  * THE AUTOSAVE KEY now carries the item NAME (`id:qty:price:name`) — a
    rename changed nothing in the old key, so neither the 600ms autosave
    nor the leave-save ever fired for one; under v1.6.45 only the (now
    removed) footer Save persisted renames. The V1646 battery caught this
    as a failing test before it could eat a real rename.
  Next is armed whenever there's a line to commit OR something payable
  (`isNotBlank() || effAmount > 0`); ≤ 0 still never persists.

**#4 — the title input with just the bottom border:** the canvas header's
static "Annotated calculation" label became a real single-line
BasicTextField whose ONLY decoration is a bottom hairline (`drawBehind`
line — no box, no background, no border), placeholder = the old label
(`ee.calcTitlePh` ×5 languages: Title · ርዕስ · Mata-duree · العنوان ·
ኣርእስቲ). The typed title rides the entry as the new optional
`LedgerEntry.calcTitle` (old rows decode without it, old code ignores it,
the Downloads backup mirrors it for free — the exprNote pattern), rides
the autosave key, headlines the COLLAPSED band (in the generic label's
place) and heads the WHOLE-LEDGER EXPORT (`formatCalcLedgerExport(title =
…)` — "march rooms\n\nrooms 300 = 300 …"), on both the canvas copy button
and the modal's.

**#5 — the fonts, de-bulked ("now it looks to bulky"):** the active line
renders 18sp MEDIUM in BOTH modes — the QWERTY field dropped SemiBold,
and the native num field dropped its hard `Typeface.BOLD` for
`sans-serif-medium` at NORMAL with tight 0.01em tracking
(`NoImeNumberField` grew a `bold: Boolean = true` parameter; the dialer,
the keypad sheet and the plain calculator keep the old look, iOS renders
Medium). The live "= total" went 20sp ExtraBold → 21sp SemiBold, the
sum-total amount F.body ExtraBold → 17sp SemiBold, the TOTAL label
ExtraBold → SemiBold, and the keypad glyphs lightened (digits 24sp Bold →
23sp SemiBold, operators 21 → 20sp). Same tap targets, calmer read.

## Harness notes

  * The store is a JVM singleton ACROSS CLASSES: V1640's 250-entry from an
    earlier class poisoned V1646's `count{amount==250}==1` — the new
    battery uses amounts no other test writes (275/345) and ID-based
    same-entry checks.
  * Committed lines serialize with the ` @date` marker — assertions that
    were written against save-the-ACTIVE-line exprNotes now strip the
    marker (V1640 test 1).
  * A false alarm during the round: the terminal display eats the literal
    `[m` sequence in `makePay[makePay.…]`, which made the committed
    v1.6.45 test file LOOK corrupted; byte-level od/python proved the
    committed code was always fine — no fix needed, and a lesson about
    verifying display anomalies before "fixing" them.
