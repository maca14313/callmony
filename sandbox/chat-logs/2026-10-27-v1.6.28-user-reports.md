## Decode + fix map

### Report 1 — "still opens slow and there is some flash when it opens"

Two separate defects, both at the very start of the app's life:

**THE FLASH.** Until hydrate publishes the persisted settings, the store's
in-memory settings are the DEFAULTS (`theme = "auto"`, `language = "en"`) —
and the boot SPLASH renders from them. So a dark-theme user saw:

  dark system splash (MainActivity has applied Theme_Callmony_Dark since
  v1.6.16) → LIGHT Compose splash — the flash — → dark main UI once hydrate
  published.

An am/om/ar/ti user saw a smaller flash of the same class: the splash tagline
in English before the persisted language landed. FIX (three parts):

- `AppStore.seedBootAppearance(sysDark, themeDark, lang)` — new, called by
  MainActivity BEFORE `setContent` (and by the iOS MainViewController for
  parity): installs the persisted theme + language + the OS dark flag into
  the store BEFORE the first Compose frame, so frame 1 of the splash already
  carries the user's appearance. Guarded — a no-op once hydrated, so an
  activity recreate can never clobber real settings.
- MainActivity extracts the language with the same cheap prefs string-scan
  it already used for the theme; iOS uses the new
  `AppStore.scanPersistedBootPrefs()` (same scan over the kv settings row).
- The splash → main UI swap itself no longer hard-cuts: a ONE-SHOT 220 ms
  fade (`SplashExitFade`) rides on top of whatever the hydrated frame
  rendered. Terminating animation (the v1.6.19 freeze lesson was an INFINITE
  spinner; this is a single bounded tween that removes itself); runs once
  per process; never replays on rotation; and if the boot loads finish
  before the first frame the splash never shows at all (nothing to fade).

**THE SPEED.** v1.6.27 parallelized the four boot loads, but hydrate still
only STARTED from a `LaunchedEffect` — i.e. AFTER the first frame was
composed and applied. On a low-end device first-frame Compose init costs
hundreds of ms that the file reads could have overlapped. FIX: hydrate is
now kicked from the platform entry point BEFORE `setContent`
(MainActivity.onCreate / MainViewController before composition) — the boot
file reads (settings, call-log cache, contacts cache, PIN) now overlap
first-frame init. `AppStore.hydrate` is idempotent (a `kotlin.concurrent.
Volatile` single-shot latch), so the CallmonyApp LaunchedEffect call that
remains is a guarded no-op — and the splash bail-out, single-writer
publishing, and boot harnesses all ride the same unchanged path.

### Report 2 — the long-press call-card sheet gains a phone-numbers strip

Long-pressing a call CARD opens the per-row action sheet (Call · WhatsApp ·
SMS · Copy number · Favourite · Call history · Create/Add contact · Delete).
The user wants the contact's PHONE NUMBER OPTIONS in that sheet too — as ONE
horizontally-scrolling row at the TOP, with the same controls the
choose-a-number picker already carries (v1.6.27), and copy by long-press.

FIX: `CallRowSheet` now renders a numbers strip above the action rows when
the call belongs to a saved contact with phones — a horizontal `ScrollRow`
of `NumberTile`s, one per DISTINCT number (same dedupe key as the picker):

- tile top row: the LABEL pill (Mobile/Work/…) + the FAVOURITE star —
  set/UNSET, live from state.contactX so the star flips the moment it is
  tapped, exactly like the picker;
- tile bottom row: the pretty number + the COPY icon + the CALL icon —
  the same icons in the same roles as the choose-a-number sheet;
- tapping the tile calls that number; LONG-PRESSING the tile copies it
  (same toast), matching "to copy even by long press";
- the strip is a HORIZONTAL scrollable inside the sheet's VERTICAL
  scrollable — different axes, safe (the v1.6.25 More-sheet crash was a
  vertical-inside-vertical infinite-height measure);
- a hairline separates the strip from the action rows, which are unchanged.

Regression coverage: `CallRowSheetStripTest` (Robolectric) long-presses a
real call card, waits for the sheet, and asserts BOTH distinct numbers
render as tiles (reaching the assertions is itself the measure-crash
guard), plus the boot went through the new entry-point hydrate latch;
`V1628Test` covers the seed semantics (installs theme+language+osDark,
normalizes unknown languages, inert once hydrated).
