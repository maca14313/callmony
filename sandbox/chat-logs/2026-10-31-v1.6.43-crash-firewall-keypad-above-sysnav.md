## 1 — "still crashing" → the firewall the user prescribed

The v1.6.42 round already: proved the Compose layer innocent in the
harness (300 rapid keys, flat 2 ms each), guarded the EditText's focus
requests, cached its cosmetic writes, and gated the per-keystroke
autosave key. The user still sees the lag-then-close on their device —
and this time they prescribed the cure themselves: "make it to log the
error and automatically copy it to clipboard".

So v1.6.43 ships GROUND TRUTH, in two capture paths through one funnel
(`androidMain/…/CrashFirewall.kt`, installed from CallmonyApplication):

- **Uncaught exceptions, any thread** —
  `Thread.setDefaultUncaughtExceptionHandler`: a full report (kind,
  timestamp, version, Android/device, thread, BootTrace phase,
  foreground, uptime, capped stack) → LOGCAT (`CallmonyCrash`) →
  `files/crash-last.txt` → `files/crash-history.log` (256 KB rolling) →
  **the CLIPBOARD, synchronously** — the crashing thread is still alive
  inside the handler, and a main-looper post would never run when the
  crash is ON main (a posted retry covers background-thread clipboard
  refusals). The previous handler chains afterwards: the system's own
  crash processing (dialog, tombstone, death) is untouched.
- **The ANR watchdog** — "it starts to lag, and finally the app closes"
  is the progressive-main-blockage signature, and an ANR is NOT an
  exception: no uncaught handler ever fires. A MIN_PRIORITY daemon
  heartbeats the main looper every 1.5 s; 6 s+ without a beat while the
  app is FOREGROUND (resumes counted — a frozen cached process can never
  false-positive) dumps the LIVE main-thread stack through the same
  funnel, labelled MAIN THREAD BLOCKED, one dump per 30 s — BEFORE the
  system ANR dialog, so the clipboard already holds the evidence when
  the "app isn't responding" screen appears.
- **The next-boot hand-over** — every captured report leaves
  `crash-pending.marker`; the next MainActivity boot re-copies it to the
  clipboard and toasts "Crash report copied to clipboard — paste it to
  send it" (`diag.autoCopied`, translated ×5 languages). Even if the
  crash-time copy failed, the trace is one long-press → Paste away.

Everything is exception-proof by construction and a NO-OP under
Robolectric (the harness boots the real Application; the capture path
itself stays directly testable).

## 2 — the keypad off the phone's navigation bar

The v1.6.41 root-slot keypad reached the WINDOW BOTTOM — under the
system gesture bar / 3-button nav, exactly what the user reported. The
fix keeps the v1.6.41 covering behaviour (the keypad still overlays the
APP's bottom nav) and stops at the phone's nav:

- `navigationBarsPadding` INSIDE the host (before `.height(CALC_PAD_H)`):
  the ± 0 . − row never enters the gesture zone; the keys keep their
  full 224 dp.
- The canvas-coloured background sits OUTSIDE the padding — the
  system-nav band stays filled (no see-through hole under the keypad).
- The grid gains real bottom padding (10 dp).

**The reservation had to be re-derived, and a real bug was caught in the
process**: the old `padLift = CALC_PAD_H − navBelowDp` arithmetic
silently assumed the keypad reached the window bottom. The new canvas
code measures DIRECTLY — the keypad reports its top edge in window
pixels (`RootBottomOverlays.overlayTopPx`), the canvas pairs it with its
own measured bottom edge, covered = canvasBottom − keypadTop. (First
draft inverted the subtraction and would have reserved NOTHING — caught
on paper before any build.) Inset-independent by construction: the
sysNav slice the keypad gave up and the sysNav slice the app nav's own
navigationBarsPadding adds cancel out — the covered band is exactly
224 − 71 = 153 dp on gesture, 3-button, or inset-free devices alike.
