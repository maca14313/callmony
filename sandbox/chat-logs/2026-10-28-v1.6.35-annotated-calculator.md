## Bonus bug found by the new tests (a REAL save-blocker)

The toast pill carried an EMPTY `clickable {}` — it swallowed every tap over
its bottom-center footprint (exactly where sheet footers render Save) and did
nothing with it. Save → immediately edit the next entry → tap Save within the
3s toast window = the tap silently eaten, nothing saved. The pill is now
click-through; only the Undo label stays tappable. This reproduced as a test
failure (quickTab after the ownership test in one JVM) and was root-caused via
a Save-enabled semantics assertion — the button was ENABLED, the tap was being
eaten above it.

## Parser rules (parseExprNote, pure, 15-case ExprNoteTest)

- everything after the first `=` is the user's own written result — never parsed
- Arabic-Indic (٠-٩) / Eastern (۰-۹) digits normalize to Latin
- glued operators split only BETWEEN digits (2x2, 100+300, 10/2, 100−50); chains like 5-3-1 work; words like "taxi"/"no-cost" never match
- an operator counts only BETWEEN two numbers (dangling "100 +" mid-typing ignored)
- comma is the decimal separator (like every amount field)
- adjacent numbers fold as an explicit + and the extraction SHOWS it (100 + 200)
- × ÷ bind tighter than + −; ÷0 drops the operator (100 ÷ 0 → 100)
